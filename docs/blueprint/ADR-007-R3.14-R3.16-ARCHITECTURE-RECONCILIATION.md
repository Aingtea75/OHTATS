# ADR-007 — R3.14–R3.16 Architecture Reconciliation

**Status:** REVIEW
**Date:** 2026-08-15
**Decision Scope:** R3.14 AI Council, R3.15 Portfolio/Cross-Account Risk, R3.16 Market Regime & Adaptive Runtime

---

## 1. Context

The Stage 3 evidence audit identified that OHTATS has substantial governance and architectural documentation for R3.14 and R3.15, while R3.16 concepts are largely absent. The audit also confirmed that several baseline documents remain in `REVIEW` status.

Per the Project Constitution, blueprint work precedes implementation, the Git repository is the project source of truth, and material architectural changes require documented review and change control.

This ADR therefore records the architectural direction before implementation begins.

## 2. Decisions

### R3.14 — AI Council

**Decision: RECONCILE / HARDEN.**

The existing AI Council canonical ownership is retained. Existing governance, authority boundaries, provider abstraction, review, disagreement, consensus, and decision-record concepts remain canonical in the existing AI Council documentation.

R3.14 work may harden missing integration details, but must not create a competing AI authority or permit Council output to bypass authorization, risk, trading, or audit controls.

Production Council/provider runtime implementation remains a separate implementation phase and must not be inferred from documentation or fixture tests.

### R3.15 — Risk

**Decision: EXTEND EXISTING RISK_MANAGEMENT CANONICAL HOME.**

`docs/blueprint/RISK_MANAGEMENT.md` remains the canonical owner for risk policy, evaluation, limits, emergency protection, risk envelopes, and adaptive risk controls.

R3.15 extensions must preserve the Risk Manager as the risk authority and must explicitly define, before implementation, the missing semantics for cross-account exposure, constraint precedence/arbitration, requested versus effective risk, and deterministic emergency recovery conditions.

No duplicate risk authority may be introduced in Trading Engine, Strategy Runtime, AI Council, or other modules.

### R3.16 — Market Regime & Adaptive Runtime

**Decision: FORMALIZE FIRST — IMPLEMENT LATER.**

R3.16 concepts must first be specified and reviewed as architecture. Implementation is blocked until the required ownership, interfaces, lifecycle, and acceptance criteria are approved.

The formalization must address at minimum:

- market-regime states, confidence, detection, transition, and invalidation;
- market-quality abstraction, including spread, liquidity, slippage, freshness, and disorder signals;
- event-risk abstraction, severity, windows, and trading restrictions;
- risk-envelope identity, version, validity, and invalidation;
- strategy eligibility under current market conditions;
- adaptive strategy behavior;
- adaptive execution timing and order-type selection;
- adaptive slippage tolerance and pending-order behavior;
- adaptive risk constraints;
- hysteresis, cooldown, and recovery behavior.

No R3.16 implementation may be treated as authoritative until this formalization is approved.

## 3. Authority Matrix

| Area | Canonical Owner |
|---|---|
| R3.14 AI Council | `A_COUNCIL_PROTOCOL.md` and `ai/council/*` |
| R3.15 Risk | `RISK_MANAGEMENT.md` |
| Market Regime | Market / Strategy Runtime |
| Market Quality | Market Data / Trading Runtime |
| Event Risk | Risk Management |
| Risk Envelope | Risk Management |
| Adaptive Risk | Risk Management |
| Strategy Eligibility | Strategy Runtime |
| Adaptive Execution | Trading Engine |
| Hysteresis / Cooldown | Regime / Adaptive Runtime |

Ownership assignments are architectural direction, not proof that corresponding runtime implementations already exist.

## 4. Constraints

1. Project Owner remains the final authority under existing governance.
2. Risk controls remain mandatory for executable trading actions.
3. Trading Engine remains the owner of execution lifecycle.
4. Strategy/deployment/account binding must remain consistent with ADR-006 and the database baseline.
5. Generic events must not be interpreted as event-risk governance without an explicit risk model.
6. Market-quality fields in persistence/backtest documents must not be treated as a unified runtime abstraction until formally specified.
7. Documentation, fixture tests, and production runtime must remain explicitly distinguished.

## 5. Consequences

### Positive

- Prevents duplicate authority and conflicting canonical ownership.
- Creates a controlled governance gate before R3.16 implementation.
- Preserves existing canonical homes for AI Council and Risk Management.
- Makes implementation status distinguishable from documentation evidence.

### Negative

- R3.16 implementation is intentionally delayed until formalization is approved.
- R3.15 requires additional architectural specification before executable risk behavior can be claimed.

## 6. Implementation Gate

The next work stages are:

1. Review this ADR against the Constitution, Architecture, Module Specification, Risk Management, AI Council, Trading Engine, Database Design, Event System, and ADR-006.
2. Resolve any ownership or terminology conflict discovered during review.
3. Update canonical documentation only after this ADR is accepted.
4. Perform R3.14 hardening and R3.15 extension.
5. Formalize R3.16 architecture.
6. Run evidence and consistency audits.
7. Only after approval, begin implementation.

## 7. Non-Goals

This ADR does not implement the AI Council runtime, provider adapters, Risk Manager runtime, Trading Engine runtime, market-regime runtime, adaptive execution runtime, or adaptive risk runtime.

It also does not approve the current architecture baselines as `APPROVED` or `LOCKED`; their existing governance status remains authoritative until separately reviewed.
